# Full Integration

Use this branch only when the user explicitly asks for a whole-Wiki audit,
reorganization, repair, or synthesis pass. A normal capture request does not
authorize a full-library sweep.

## Establish Scope

Read the repository purpose, schema, indexes, logs, source-role conventions,
maintenance scripts, and recent structural changes. Resolve review-only versus
implemented integration from the current request; ask only when it remains
unclear.

Use the shared provenance contract to judge source-family boundaries, raw
fidelity, translations, mirrors, and independent interpretations.

Do not silently expand the run into broad external research, mass source
ingest, schema migration, destructive moves, or rewriting every page. Research
or propose those separately when evidence shows they are needed.

## Build The Audit

Inventory the Wiki using repository scripts and lightweight searches over:

- raw-to-source-summary provenance
- source families, mirrors, translations, and independent interpretations
- canonical owners and duplicated claims
- broken, stale, or misleading links
- weakly supported or overconfident claims
- conflicting decisions and superseded procedures
- concepts that have sources but no integration
- summaries that should merge and merged pages that should split
- indexes, queries, logs, and orphan pages

Use the repository's graph and metadata rather than treating filenames as the
only structure.

## Prioritize By Knowledge Value

Prioritize repairs that improve trust, reuse, or discoverability:

1. incorrect claims and dangerous stale procedures
2. broken provenance and wrong source-family merges
3. duplicate or missing canonical ownership
4. high-value sources not woven into concepts
5. cross-links and navigation gaps
6. new synthesis created by genuine tension across sources

Create a new concept only when it owns a durable idea that would be less
discoverable inside existing pages. Keep open questions separate from
evidence-backed conclusions.

## Delegate Across Real Perspectives

Prefer multiple agents for full integration when the host supports them.
Separate roles such as structural audit, provenance audit, concept correctness,
SOP freshness, synthesis, skeptical review, and final acceptance. Give each
role independent evidence or a distinct acceptance criterion.

The main agent defines the boundaries, verifies findings against repository
evidence, resolves duplicate recommendations, and owns the final diff. A failed
agent does not block the audit when the remaining evidence is sufficient.

## Execute In Reviewable Batches

For a large Wiki, first produce a review list grouped as:

- duplicates
- wrong merges
- should-merge pages
- provenance gaps
- stale or disputed knowledge
- missing integration

Ask before any material schema choice or ambiguous canonical merge. Then repair
in small, verifiable batches rather than one opaque rewrite.

Full Integration is complete when the requested audit scope is accounted for,
accepted repairs satisfy the shared integration contract, and unresolved
issues remain explicit. Review-only mode stops after the prioritized audit and
proposed batch plan.
